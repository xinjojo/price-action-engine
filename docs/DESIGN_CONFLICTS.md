# 第一部分：设计内部的矛盾

## C1. Setup 只能读单个 Snapshot，但 Brooks 形态本质上是时序的 ★★★

**矛盾**：需求 §6 写"Setup 原则上只能读取 `MarketStateSnapshot`"。但 Brooks 的形态（H2、Wedge、MTR）定义的是**连续多根 bar 之间的关系**——"H2 = 在一个 swing high 之后回撤，再上破"。单日 Snapshot 描述的是"当前状态"，不含"上一根 bar 是什么"这类关系。

如果 Setup 只能拿到一个 Snapshot，它无法表达任何跨 bar 形态。

**三个解法**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| (a) Snapshot 窗口 | Setup 读最近 N 个 Snapshot 的只读序列 | 边界保持（不碰原始 K 线、不重算指标）；可表达时序 | 需要定义"窗口长度由谁决定" |
| (b) 把历史编码塞进单个 Snapshot | 增加 `prev_bar_*` / `bars_since_*` 等字段 | Setup 接口最简单 | **违反 Core 不应知道 Setup 的原则**——"要塞多少历史"取决于未来做什么 Setup |
| (c) 独立 `SetupContext` 对象 | Core 提供最近 N 个 Snapshot 的只读视图 | 与 (a) 等价，但边界更显式、可单独测试 | 多一个对象 |

**我的倾向：(c)，退而求其次 (a)。** 核心约束（不碰原始 K 线、不重算 Core 指标）在三种方案下都成立，所以这不破坏架构，只是需要把"单数"改成"序列"。

**需您裁决**：接受 `Setup.detect(snapshot_window: Sequence[MarketStateSnapshot])` 吗？窗口长度由 Setup 自己声明（类似 `required_fields`）还是由框架统一给？

## C2. "订单只有效 1 根 bar" 有两种情况，需求只覆盖了一种 ★★★

**矛盾**：需求 §29 的文字是"triggered=true, filled=false 则原订单失效"。但存在两种完全不同的情况：

| 情况 | 含义 | Brooks 实际做法 |
|---|---|---|
| (a) **未触发**（`high < trigger`） | 价格根本没到 | 交易者通常**继续挂着**同一个 stop 订单 |
| (b) **已触发但未成交**（一字板） | 价格越过了，但买不到 | 订单作废，重新评估 |

§29 的例子是 (b)，但表述容易让人以为 (a) 也要作废。

**V0.1 保守建议**：两种情况都作废。理由：保守、可证伪、且强制"逐 bar 重新读 Snapshot"这个好习惯。

但必须明确：**这是保守假设，不是 Brooks 原意。** 如果后续要做 Brooks 风格的连续挂单，需要引入 `OrderSpec.roll_forward` 开关。

**需您裁决**：V0.1 两种都作废，还是 (a) 可延续（并每日重新确认 Setup 仍成立）？

## C3. `structure_bias` 与 `trend.bias` 可能冗余 ★★

两者的定义都是"净位移 / ATR"。如果窗口参数相同，它们就是同一个数的两个名字。

**建议**：明确拉开尺度——

- `structure_bias`：基于**已确认 swing 点**序列（默认最近 4 个 swing），跟随结构，反应慢
- `trend.bias`：基于**固定交易日窗口**（默认 20 日）的净位移，反应快

尺度不同则两者都有信息量（结构 vs 价格的背离本身是信号）。

**需您裁决**：保留两个，还是删掉 `structure_bias`？如果保留，参数必须拉开。

---

## C4. "不得自动修正数据" vs "停牌日必须补 gap bar" 是否自相矛盾 ★★

**我的判断：不矛盾，但必须严格定义。**

补 gap bar 是**序列化完整性**要求，不是数据修正。区别在于：

- ✅ 允许的：在时间序列中插入"该交易日存在但无成交"的占位记录，其 OHLC 一律为 `None`，`is_suspended=True`，`quality_flags += ("GAP_BAR",)`
- ❌ 禁止的：用前收盘价填充、用插值填充、用任何"看起来合理"的价格填充

**gap bar 的 OHLC 必须是 `None`，不是前收。** 填前收会制造 `range=0, body=0` 的假十字星——正是需求 §21 要避免的那类错误。

---

## C5. `ATR` 在连续一字板期间会失真 ★★

**问题**：连续一字涨停时，从第 2 天起 `H - L = 0` 且 `|H - C_prev| = 0`，`TR = 0`。

Wilder ATR 会把这些 0 纳入平滑，导致 ATR 被系统性拉低 ⇒ 所有 `score_atr()` 的分数被推高 ⇒ 一字板密集期产生大量虚假的"极强信号"。

**建议**：ATR 计算时**跳过 `TR == 0` 的 bar**（不纳入 Wilder 平均的分母），并在 `quality_flags` 标注 `ATR_DEGRADED`。

**需您裁决**：接受"跳过 TR=0"吗？代价是一字板密集期 ATR 更新停滞（但比拉低更安全）。

---

## C6. 涨跌停会截断突破强度测量 ★★

**问题**：一只票以涨停方式突破 swing high，但被限制在 +10%，无法进一步延伸。此时 `breakout.strength`（= |close − reference_level| / ATR）会被**系统性低估**——不是因为它弱，恰恰因为它强到封板了。

**建议**：`limit_status ∈ {UP_LOCKED, DOWN_LOCKED}` 时，给 breakout 打 `STRENGTH_CAPPED_BY_LIMIT` flag，让下游知道这是一个被制度截断的测量值，而不是真实的弱突破。

**需您裁决**：加 flag，还是在 `breakout.strength` 里做制度补偿？我倾向**只加 flag 不做补偿**——补偿等于人为调数，会污染后续的预测力检验。

# 第二部分：Brooks 理论与 A 股制度的冲突

## C7. A 股的"信号频率"与"可执行信号频率"是两个数 ★★★

Brooks 的整套风险回报计算（入场 − 止损 = 1R）隐含假设"价格到了就能成交"。A 股一字板打破了这个假设。

**后果**：如果回测只统计"产生了多少信号"，会得到严重虚高的机会数。真正重要的是"有多少信号**实际能成交**"。

**建议**：V0.2 起所有评估必须同时报告三个数：

```
signals_generated      信号数
signals_fillable       可成交信号数（排除一字板锁死）
fill_rate              = fillable / generated
```

并按 `tradability_score` 分层报告。`fill_rate` 过低意味着这个 Setup 在 A 股根本不可执行，无论回测多好看。

---

## C8. T+1 使实际风险大于 Brooks 模型的假设 ★★★

Brooks（美股）可以当天入场、当天止损。A 股不行。

**后果**：
- 隔夜风险无法当日对冲。一个在 T 日尾盘恶化的持仓，只能 T+1 处理。
- Brooks 的"止损很近所以风险很小"在 A 股不成立——止损近不代表能及时执行。
- 任何依赖"当日反向信号即出场"的 Setup 在 A 股都要延后一天。

**建议**：Execution 层必须显式区分 `stop_trigger_date` 与 `stop_fill_date`，并在评估中统计"止损滑点"（`stop_price` vs 实际 `fill_price`）。

---

## C9. 涨跌幅限制会改变 measured move 的到达率 ★★

Brooks 的 measured move / 目标位经验值来自美股。A 股有 ±10%/20% 限制，但**方向有利时也可能一步到位**：一个 10% 涨停可能直接覆盖原本需要数日的目标位。

**后果**：A 股的"目标位到达率"会**系统性高于**美股经验值。直接照搬 Brooks 的胜率/盈亏比预期会产生误判。

**处理**：不修正模型，只在评估时注明"目标位到达率含制度放大效应，不可与美股经验值直接比较"。

---

## C10. 一字板几何退化，但它是 A 股最常见的"强趋势 bar" ★★

已通过 `bar_bias` 语义覆盖处理（见 Snapshot 文档 §3.1）。此处补充一个未处理的次生影响：

一字板会让 `range_atr_ratio = 0`，如果任何下游逻辑用"range 小 ⇒ 弱"来判断，就会把一字板判成弱势 bar。**必须确保没有任何代码路径把 `range == 0` 解释为弱。**

建议在 `test_bar_features.py` 中加一条断言：一字板 bar 的 `bar_control_score` 必须 `> 90`。

# 第三部分：无法真正客观量化的字段

## C11. `exhaustion_score` / `compression_score` 推迟到 V2 ★★★

| 字段 | 问题 |
|---|---|
| `exhaustion_score` | "耗尽"本质上需要知道**后续是否反转**才能定义——它是一个事后概念。用历史数据构造的任何代理指标，都是在用"事后看起来像耗尽"的形态去预测反转，属循环论证风险 |
| `compression_score` | 与 `range.score` **高度重叠**——`range.score` 高（Kaufman ER 低）本身就意味着价格压缩。重复概念 |

**建议**：V0.1 不实现。若 V2 要做，必须先回答"它相对 `range.score` 的增量信息是什么"。

---

## C12. `trend.confidence` 是未校准的启发式 ★★

我的定义是 `warmup × (1 - chop_ratio)`。它看起来有意义，但：

- 它不对应任何可观测的真值
- 无法通过任何检验被证伪
- 三个参数（warmup_bars、chop 定义、乘积形式）都是拍的

**这是最容易自我欺骗的一类字段**——名字让人以为它有用，但它只是把两个已知量重新组合了一下。

**建议（三选一）**：
1. 明确定义它要预测什么（如"未来 N 日趋势延续"），用历史数据**校准**成一个真实的概率
2. 保留但改名为 `trend_stability`，去掉"confidence"这个暗示可靠性的名字
3. 删除

**我倾向 (2)**：改名为 `stability`。它确实度量了"路径是否干净"，这是客观且有意义的；但叫 confidence 会诱导下游过度信任。

**需您裁决**。

---

## C13. `climax_score` 的权重是主观的 ★

我给了 `w1=w2=w3=1/3`。这个权重没有理论依据，只是均分。

**这不致命**（climax 的三个分量——波动放大、量能放大、偏离均线——都是有客观依据的），但**必须做预测力检验后才能决定是否保留**：

> 按 `climax_score` 分层，看未来 N 日收益是否单调。如果分位数分组收益没有单调性，这个字段就该删。

**这一点适用于所有 Level B 变量**，见 C17。

# 第四部分：日 K 数据无法知道的信息

## C14. 同一根 bar 内无法判断触发顺序 ★★★

日 K 只有 O/H/L/C，不知道当天是先到 high 还是先到 low。

**后果**：同一根 bar 内，止损位和入场触发位都被触及 ⇒ 无法判断哪个先发生。这是需求 §27 未覆盖的情形。

**保守规则**：同一 bar 内 stop 与 entry 都被触及 ⇒ **假设先触发止损**（最坏情况）。

**需您裁决**：接受"最坏情况优先"吗？另一种选择是"先入场后止损"（乐观），会高估收益。

---

## C15. 无法知道该价位是否有足够流动性 ★★

日 K 无法区分"价格触及某价"与"该价位有足够的对手盘"。只能靠保守规则（一字板不成交）近似。

**已知偏差**：`tradability_score` 只用了换手率做流动性代理，没有考虑：
- 封单量（一字板能看出来，但普通封板看不出）
- 盘中挂单分布
- 大单冲击成本

V0.1 接受这个偏差（需求 §28 明确禁止排队模拟）。

---

## C16. 幸存者偏差 ★★

退市股的历史数据可能不完整，甚至被数据源清理。任何基于"当前股票列表"的回测都会系统性高估收益。

**V0.1 不处理**（它属于组合层问题），但必须知道它存在。

**V0.2 建议**：用 `stock_basic` 的 `delist_date` 保留退市股，用 a-stock-data 的 `baostock_stock_basic` 补充退市日（见 DATA_LAYER §3.5）。

## C17. 其他不可知项（清单）

| 项 | 影响 | V0.1 处理 |
|---|---|---|
| 盘中触发时点 | 无法模拟日内多次交易 | 不处理 |
| 集合竞价价格形成 | 开盘价的形成过程不可见 | 按 `open` 成交 |

# 第五部分：方案建议（超出需求，供参考）

## C18. V0.2 的第一件事应该是"验证变量"，不是"写策略" ★★★

需求 §44.8 说"能逐步验证每个变量是否真的有预测价值"，§45 说"先验证底层状态变量，再增加大量 Setup"。

**具体建议**：在写任何 Setup 之前，先对每个 Level B 变量做**单变量预测力检验**：

```
1. 全样本计算 Snapshot
2. 对每个变量，按分位数分 5 组
3. 检查未来 N 日收益（N = 1/3/5/10）是否在分组上单调
4. 计算 IC（信息系数）及其时间序列稳定性
5. 只有通过了检验的变量，才允许出现在 Setup 里
```

**理由**：如果 `trend.strength` 本身对 A 股日 K 没有任何预测力，那么在它之上堆多少个 H2 变体都不会有用——只会过拟合。

这是把"可证伪"落到工程流程上的唯一办法，也是本项目相对大多数交易研究项目最可能做出差异的地方。

**需您裁决**：V0.2 先做变量验证，还是先做第一个 Setup？

---

## C19. 建议建立"变量注册表" ★

每个 Level B 变量在引入时，必须登记：

```
变量名 / 定义 / 归一化基准 / 引入动机 / 预测力检验结果 / 结论（保留|观察|废弃）
```

**理由**：需求 §17 说"不要随意扩展几十个新指标"。没有注册表，"不要随意"就只是一句愿望。有了注册表，每个新变量都要交代"你比已有的好在哪"。

成本：一个 markdown 文件。收益：防止指标膨胀。
